### 1. SOP → procedimento executável híbrido (linguagem natural + código + conectores)
- **O que é**: o padrão que convergiu em 2026 entre Decagon (AOP), Intercom (Fin Procedures), Sierra (Journeys/Agent SDK) e Anthropic (SKILL.md): a política de atendimento deixa de ser prosa no system prompt e vira um artefato estruturado com (a) passos em linguagem natural, (b) ramificações if/else explícitas, (c) trechos de código determinístico para regras duras (elegibilidade, cálculo de datas, limites), (d) conectores de dados com escopo (Stripe, Shopify, CRM) e (e) sub-procedimentos reutilizáveis. Decagon descreve como "natural language instructions that compile into validated workflows"; Intercom: "combine natural language with deterministic controls… Code for precision on strict rules like eligibility checks or date calculations"; Anthropic: "instructions for flexible guidance, code for reliability, resources for factual lookup". Conversão de SOP humano → AOP em 5 passos (auditar, decompor em gatilhos/ações, mapear dados por etapa, definir pontos de decisão, adicionar validações em ações sensíveis) — porque SOP humano "relies on implicit knowledge and judgment" e o AOP precisa de "explicit, machine-executable logic".
- **Quem está shipping**: Decagon AOPs (GA; blog "From SOPs to AOPs", série 2025–2026); Intercom Fin Procedures (GA; faturadas como outcome desde 12/03/2026); Sierra Agent Studio 2.0 "Journeys" (05/11/2025) + Agent SDK declarativo com "tuning controls" de criativo↔determinístico por workflow; Anthropic Agent Skills — padrão aberto (agentskills.io) adotado por 40+ clientes incl. Cursor, Gemini CLI, Codex, GitHub Copilot, VS Code, Spring AI, Laravel Boost; disponível na Claude API via `/v1/skills` + code execution e em Managed Agents (`skills[]` com `version: latest|pinned`, até 500 por sessão, ou descoberta em `.claude/skills/` de repo montado).
- **Maturidade**: mainstream nos vendors de CX; early-adopters para quem constrói in-house com Skills (API de skills ainda depende de container de code execution sem rede).
- **Aplicação em motor de resolução**: cada intenção resolúvel (reembolso, troca de plano, reset) vira um procedimento versionado; o LLM navega os passos, o código decide elegibilidade, o conector executa. No stack Laravel/Claude: SKILL.md por procedimento + scripts PHP/Python de elegibilidade rodando fora do contexto (só o output entra), progressive disclosure (≈100 tokens por skill até ser acionada).
- **Gap vs blog**: não existe. Adjacente: `context-engineering-skill-ai-engineer-2026` e `progressive-disclosure-agente-50-ferramentas` (falam de skills/contexto para coding e de tool discovery). Ângulo novo: **SKILL.md como SOP de atendimento em produção via API/Managed Agents (não Claude Code)**, com a tabela comparativa AOP vs Fin Procedure vs Journey vs Skill e o "checklist de 5 passos SOP→procedimento".
- **Fontes**: https://decagon.ai/blog/from-sops-to-agent-operating-procedures (2025–26) · https://decagon.ai/product/aop · https://www.intercom.com/help/en/articles/12495167-fin-procedures-explained (2026) · https://sierra.ai/blog/agent-os-2-0 (05/11/2025) · https://sierra.ai/product/agent-sdk · https://agentskills.io/home · https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview · https://platform.claude.com/docs/en/managed-agents/skills (beta `managed-agents-2026-04-01`) · https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills

### 2. Agente que constrói o agente a partir de SOP/transcrições (e como medir se construiu certo)
- **O que é**: uma camada acima do item 1: um "developer agent" lê SOPs, transcrições de chamadas, gravações de áudio ou fotos de quadro branco, extrai comportamentos e edge cases, e gera o procedimento/agent completo. Sierra lançou o Ghostwriter (25/03/2026) com essa promessa; Decagon lançou o Duet (02/04/2026), que "builds and refines AOPs" analisando transcritos e — detalhe relevante — roda ele mesmo sobre AOPs. Para medir isso, Sierra publicou o Hyper-τ-bench (τ^τ-bench, 2026): o agente-desenvolvedor recebe os registros de um negócio simulado, constrói um agente de atendimento em sandbox e é pontuado pelo desempenho desse agente em tarefas held-out.
- **Quem está shipping**: Sierra Ghostwriter (GA para clientes, 25/03/2026); Decagon Duet (03–04/2026); Hyper-τ-bench (Sierra Research, 2026).
- **Maturidade**: early adopters. Evidência dura do Hyper-τ-bench: Claude Opus 5 (max reasoning) sozinho atinge **23,9%**; o mesmo modelo com um engenheiro experiente no loop, **82,2%**. Cinco modos de falha: recuperação incompleta de requisitos, não "entrevistar" o cliente, erros econômicos, pouca exploração de design e tentativas de trapaça em 17–42% dos testes.
- **Aplicação em motor de resolução**: bootstrap do catálogo de procedimentos a partir de tickets históricos + SOPs, com humano revisando o diff de cada AOP gerado; o Duet também fecha o loop (transcrito → proposta de mudança no AOP → simulação → deploy).
- **Gap vs blog**: não existe. Adjacente: `agent-improvement-loop-melhora-proprio-codigo` (auto-melhoria em código). Ângulo novo: o loop transcrito→procedimento em suporte e o dado de 23,9% vs 82,2% como argumento de "humano no design, não só na aprovação".
- **Fontes**: https://sierra.ai/blog/hyper-t-bench-evaluating-agents-that-build-agents (2026) · https://decagon.ai/blog/why-we-built-decagon-duet-on-agent-operating-procedures (02/04/2026) · https://winbuzzer.com/2026/03/26/sierra-ghostwriter-self-service-ai-agent-builder-xcxwbn/ [secundário, 26/03/2026] · https://sierra.ai/blog/agents-as-a-service

### 3. Verificador de política como sub-agente: de "guardar uma ação" para "guiar o procedimento inteiro"
- **O que é**: em vez de um guardrail que olha só a chamada de ferramenta (argumentos), um verificador separado com acesso ao diálogo completo e à política, invocado (a) por tool call — PolicyGuard — ou (b) em cada fronteira de turno do usuário, sobre um grafo de workflow compilado a partir da política — PolicyGuide. Cobre as duas famílias de falha do τ²-bench: ação proibida (conceder mudança a cliente inelegível) e **omissão procedimental** (pular verificação de identidade ou confirmação). O verificador devolve feedback conversacional acionável ("falta confirmar X antes de Y"), não só allow/deny. JourneyBench (jan/2026) chega a conclusão parecida por outro caminho: um Dynamic-Prompt Agent que modela explicitamente o controle de política supera prompt estático (GPT-4o-mini com DPA passa GPT-4o com SPA em aderência).
- **Quem está shipping**: papers (KAIST — Kang, Yu, Hwang): PolicyGuard (28/06/2026), PolicyGuide (20/08/2026); JourneyBench (02/01/2026). Em produto, a ideia aparece como "Testes unitários verificando conformidade política" (Decagon) e como Quality Score/LLM-judge always-on (Sierra, Zendesk [roadmap]) — mas em pós-hoc, não em runtime. Runtime proativo ainda é research.
- **Maturidade**: experimental/early. Números: PolicyGuard +12,0/+6,0/+12,0 pp de Pass^4 (GPT-5.4 / Claude Sonnet 4.6 / Gemini 2.5 Pro) no τ²-airline, bloqueando ~metade das vezes de um guard por argumento; PolicyGuide eleva Pass^4 médio de 0,42→0,62 no τ²-bench, telecom 0,19→0,61.
- **Aplicação em motor de resolução**: "dual-control" no sentido de arquitetura: agente executor + verificador (LLM pequeno ou grafo determinístico) que checa pré-condições da política antes de liberar a ferramenta de ação. Encaixa direto num harness Laravel como middleware antes do dispatch do tool call.
- **Gap vs blog**: **adjacente** a `guardrails-para-agentes-de-ia` (guardrails de segurança/formato) e `trust-layer-agente-reputacao-fonte` (confiança na fonte). Ângulo novo: **compliance de procedimento de negócio** (omissão de passo, elegibilidade), verificador condicionado no diálogo inteiro, e a evidência de que action-local guards não guiam fluxo multi-etapa.
- **Fontes**: https://arxiv.org/abs/2608.19861 (20/08/2026) · https://arxiv.org/abs/2606.29225 (28/06/2026) · https://arxiv.org/abs/2601.00596 (02/01/2026) · https://arxiv.org/abs/2506.07982 (τ²-bench, 09/06/2025) · https://github.com/sierra-research/tau2-bench

### 4. Definição operacional de "resolução" (a métrica que vira fatura)
- **O que é**: com pricing por outcome, a definição de resolução deixou de ser KPI e virou contrato. Intercom: *confirmed resolution* (cliente diz "ok, thanks") vs *assumed resolution* (cliente sai sem pedir mais); se o cliente volta à mesma conversa "even across billing periods", a resolução é deduzida; cobra 1x por conversa; *Procedure handoff* também é outcome cobrado (US$0,99) desde 12/03/2026. Zendesk: resolução automatizada conta após **72h de inatividade** se uma avaliação por IA confirmou que a resposta foi relevante; se o bot só recomendou artigo, o cliente precisa ter clicado; reply generativa não exige clique. A prática de engenharia que emergiu (Richpanel, 2026) substitui "deflection" por 5 medidores: taxa de resolução **correta** sem toque humano, contagem de ações incorretas, precisão/recall de escalação, **taxa de recontato em 7 dias** e custo por conversa genuinamente resolvida.
- **Quem está shipping**: Intercom Fin (US$0,99/outcome; Procedures como outcome desde 12/03/2026); Zendesk (US$1,50 comprometido / US$2,00 avulso; auto-bill de excedente desde 01/2026 [secundário]; Relate 19/05/2026: Quality Score em early access analisando 100% das interações [roadmap]); Sierra (outcome-based, "agents as a service"); Richpanel (metodologia publicada).
- **Maturidade**: mainstream (pricing) / early (instrumentação rigorosa de recontato e ação incorreta). Taxas reais: Intercom case studies 42–50% [secundário]; média 76% autônoma em jun/2026 [secundário, não verificado em fonte primária]; Sierra "até 90%" é teto de marketing.
- **Aplicação em motor de resolução**: o evento de resolução precisa ser um fato no banco com estado (assumed → confirmed → revertida por recontato), janela de observação e vínculo ao procedimento executado; sem isso o painel mente e a fatura do vendor não tem auditoria.
- **Gap vs blog**: não existe. Adjacente: `custo-agente-ia-producao-2026-planilha-tco` e `quanto-custa-agente-ia-producao-conta-tokens` (custo por token, não por outcome); `chatbot-nao-e-agente-teste-3-turnos`. Ângulo novo: **modelar "resolução" como máquina de estados com reversão**, comparar as definições Intercom vs Zendesk, e o kit de 5 métricas anti-deflection.
- **Fontes**: https://www.intercom.com/help/en/articles/8205718-fin-ai-agent-outcomes · https://www.intercom.com/help/en/articles/12495167-fin-procedures-explained (12/03/2026) · https://support.zendesk.com/hc/en-us/articles/8357756668186-About-automated-resolutions-for-AI-agents · https://www.zendesk.com/blog/zendesk-insights/innovation/relate-2026--evolving-the-resolution-platform-for-the-autonomous/ (19/05/2026) · https://www.richpanel.com/learn/evaluating-ai-support-agents-before-launch (2026) · https://www.gleap.io/blog/intercom-fin-ai-pricing-2026 [secundário]

### 5. Interrupt/resume durável: aprovação como estado serializável, não como prompt
- **O que é**: o padrão HITL de 2026 trata a aprovação humana como pausa de execução com estado persistido e retomada idempotente. OpenAI Agents SDK: `@tool(needs_approval=True|async fn)`; a run para, `RunResult.interruptions` traz `ToolApprovalItem` (agent, tool, args); `state = result.to_state()` serializa (incluindo decisões "sticky" `always_approve/always_reject`, uso, `tool_input`, retomadas aninhadas de agent-as-tool); `state.approve()/reject()`; `Runner.run(agent, state)` retoma. LangChain/LangGraph: `HumanInTheLoopMiddleware(interrupt_on={tool: {allowed_decisions: [approve, edit, reject, respond]}})` com checkpointer obrigatório (Postgres em prod) e `Command(resume={"decisions": [...]})`. Anthropic Managed Agents: política `always_ask` pausa a sessão com `session.status_idle` / `stop_reason.type = requires_action` e espera indefinidamente um `user.tool_confirmation {allow|deny, deny_message}`; webhooks notificam a pausa; `ant beta:sessions connect` permite aprovar pelo terminal. Claude Agent SDK: ordem fixa de avaliação — hooks → deny rules → ask rules → permission mode → allow rules → `canUseTool`; tool auto-aprovada por regra **nunca chega** ao callback.
- **Quem está shipping**: OpenAI Agents SDK (docs HITL, 2026); LangChain (docs 2026); Anthropic Managed Agents (beta pública 08/04/2026); Claude Agent SDK (permissions + hooks); Strands Agents, Microsoft Agent Framework/AG-UI.
- **Maturidade**: mainstream nos SDKs; o que é novo é a durabilidade (sobreviver a restart/fila) e o "edit" (humano altera argumentos antes de executar).
- **Aplicação em motor de resolução**: fila de revisão de ações sensíveis (reembolso acima de alçada, cancelamento) com o estado da conversa congelado; supervisor aprova/edita/nega e a conversa retoma sem re-executar passos anteriores. Intercom já embute escalação autônoma quando detecta loop/sem progresso/pedido explícito de humano.
- **Gap vs blog**: não existe. Adjacente: `classificacao-de-intencao-llm-roteamento-de-agente` (roteamento de entrada) e `claude-code-hooks-slash-commands-mcp` (hooks de dev). Ângulo novo: **comparativo dos 4 mecanismos de interrupt/resume** (OpenAI RunState, LangGraph Command, Managed Agents tool_confirmation, Agent SDK canUseTool) + a armadilha da ordem de avaliação do Agent SDK.
- **Fontes**: https://openai.github.io/openai-agents-python/human_in_the_loop/ · https://docs.langchain.com/oss/python/langchain/human-in-the-loop · https://platform.claude.com/docs/en/managed-agents/permission-policies · https://platform.claude.com/docs/en/agent-sdk/permissions · https://platform.claude.com/docs/en/agent-sdk/hooks

### 6. Permission policy `auto`: classificação de risco por chamada no servidor (run / deny / pause)
- **O que é**: o passo seguinte ao always_ask. Em Managed Agents, `permission_policy: {type: "auto"}` faz o servidor avaliar **cada** chamada considerando ferramenta + input + conteúdo da sessão até ali, com três saídas: executa; nega (`is_error: true`, "Permission to use {tool} has been denied", não-override pelo cliente); ou pausa por indeterminação (`reason_code: indeterminate`). Cada evento `agent.tool_use` carrega `evaluated_permission` (allow/ask/deny) e um objeto `evaluation` com `reason_code` (ex.: `high_risk`) "for your client to branch on and keep in audit records". Regra de intenção: só `user.message` conta como intenção; conteúdo de tool result, página buscada ou resposta de MCP "is assessed but not taken as instructions". Aviso explícito da doc: "`auto` is not a human checkpoint" — se alguém precisa revisar, use `always_ask`. Defaults: agent toolset `always_allow`, MCP toolsets `always_ask` (novas tools de um MCP não rodam sem aprovação).
- **Quem está shipping**: Anthropic Managed Agents (auto mode anunciado ~10/09/2026; beta header `managed-agents-2026-04-01`). Padrão análogo em Claude Code "auto mode" (já coberto no blog para coding).
- **Maturidade**: experimental/early — lançamento desta semana; só governa tools server-executed (agent toolset + MCP), não custom tools.
- **Aplicação em motor de resolução**: alçada em três faixas: `always_allow` para leitura (status do pedido), `auto` para escrita reversível (atualizar endereço), `always_ask` para irreversível (reembolso, cancelamento). E o ponto de segurança que o blog deve martelar: **se o input do cliente final é repassado em `user.message`, ele vira "intenção" e pode liberar uma chamada** — logo, tools que o cliente final não poderia rodar ficam em `always_ask`.
- **Gap vs blog**: não existe para suporte. Adjacente: `claude-code-auto-mode-padrao` (mesmo conceito, aplicado a coding) e `prompt-injection-agente-site-raspado-system-prompt`. Ângulo novo: **auto mode como política de alçada em agente voltado ao cliente** + o vetor "intenção via user.message".
- **Fontes**: https://platform.claude.com/docs/en/managed-agents/permission-policies · https://alphasignal.ai/news/anthropic-s-claude-managed-agents-now-flag-risky-actions-for-human-approval (10/09/2026) [secundário] · https://platform.claude.com/docs/en/release-notes/overview

### 7. Simulação de usuário com personas não-cooperativas (e o que o simulador esconde)
- **O que é**: testar o agente com um segundo LLM fazendo o cliente, com persona (objetivo, humor, idioma, paciência), e um terceiro LLM como juiz. Vendors: Sierra gera suites automaticamente a partir de SOPs, base de conhecimento, transcritos de coaching e fluxos; Salesforce Agentforce Testing Center oferece personas pré-definidas ("frustrated customer", "non-native English speaker", "distracted user"), multi-turn, métrica de *task resolution* e gate via `sf agent run test`; Intercom Fin Simulations (pass/fail por critério); Decagon testa AOPs contra personas mock. A pesquisa de 2026 mostra o limite: simuladores herdam "benevolence bias" — são cooperativos e homogêneos. *Lost in Simulation* (jan/2026): taxa de sucesso varia até **9 pp** conforme o LLM simulador, miscalibração sistemática (subestima em tarefas difíceis), e pior desempenho com AAVE vs SAE, agravado por idade. *Simulated Customers Never Walk Away* (jun/2026): simuladores reduzem a resistência expressa em 46% (25,1%→13,5%) — o cliente simulado nunca desiste, então funil e "resolução" inflam. *Persona Policies* (mai/2026): busca evolutiva de geradores de comportamento; anotadores cegos classificaram usuários PPol como humanos em 80,4%; +17% de sucesso relativo do agente treinado com eles.
- **Quem está shipping**: Sierra Simulations (35k testes/dia entre clientes), Salesforce Testing Center (2026), Intercom Fin Simulations, Decagon; papers arXiv 2601.17087, 2606.20708, 2605.12894, 2604.21480 (diversity-guided).
- **Maturidade**: mainstream como ferramenta; early no rigor (quase ninguém mede fidelidade do simulador).
- **Aplicação em motor de resolução**: suite de simulação por procedimento com mix forçado de personas adversas (desiste, mente, muda de ideia, fala outro dialeto), mais um "teste do simulador" — comparar distribuição de desfechos simulados vs. tickets reais antes de confiar no número.
- **Gap vs blog**: **adjacente** a `prompts-resilientes-evals-adversariais-edge-cases`, `avaliacao-de-agentes-de-ia-evals-honestos`, `evals-para-agentes-de-ia-llm-as-a-judge`, `model-graders-…`. Ângulo novo: **o simulador é um componente sob teste** — benevolence bias, disengagement deficit, variância por LLM simulador, e como construir personas não-cooperativas.
- **Fontes**: https://sierra.ai/blog/simulations-the-secret-behind-every-great-agent · https://www.salesforce.com/blog/agentforce-testing-center/ (2026) · https://arxiv.org/abs/2601.17087 (28/01/2026) · https://arxiv.org/abs/2606.20708 (16/06/2026) · https://arxiv.org/abs/2605.12894 (13/05/2026) · https://arxiv.org/pdf/2604.21480 (04/2026)

### 8. Conversation tests a partir de anotações + replay de tickets históricos como gate de release
- **O que é**: o ciclo de vida do agente como software. Sierra (ADLC): agentes são **snapshots imutáveis** (código, prompts **e versão de modelo**) com rollback instantâneo; o time de CX anota amostras de conversas diariamente no Experience Manager e **cada conversa anotada vira um teste** — "a snapshot of the conversation simulated against mock APIs to reliably reproduce the problem" — rodado em paralelo antes de cada release, via GitHub Actions/CLI, gateando o deploy "just like unit tests". Complemento pré-lançamento (Richpanel): replay de 90 dias de tickets resolvidos em dois conjuntos — *volume set* (~200 casos, proporcional à frequência de intenção; 200 casos ≈ ±7 pp de IC) e *risk set* (60–100 casos sobre-amostrados em dinheiro, exceções de política, raiva, pedidos que devem ser negados, multi-problema, casos onde humanos discordaram).
- **Quem está shipping**: Sierra (ADLC, Experience Manager, CI/CD); Decagon (regressão automatizada + version tracking + Agent Workbench para debug por trace, spring/2026); Salesforce DevOps Testing Center (quality gates bloqueiam deploy); Richpanel (metodologia).
- **Maturidade**: mainstream nos vendors; early in-house.
- **Aplicação em motor de resolução**: pipeline CI do harness: (1) replay dos conjuntos volume/risk com mocks dos sistemas, (2) suite de conversas anotadas como regressão, (3) snapshot com pin de modelo, (4) gate. O pin de versão do modelo no snapshot é o detalhe que separa isso de "rodar evals".
- **Gap vs blog**: **adjacente** a `pipeline-eval-continuo-prompts-producao` e `tdd-com-agentes-testes-que-sobrevivem` (coding). Ângulo novo: **anotação de conversa → teste de regressão com mock de API**, amostragem volume/risk com IC, e snapshot imutável incluindo versão do modelo.
- **Fontes**: https://sierra.ai/blog/agent-development-life-cycle · https://decagon.ai/blog/spring26-product-launch (03/2026) · https://www.salesforce.com/blog/agentforce-testing-center/ · https://www.richpanel.com/learn/evaluating-ai-support-agents-before-launch

### 9. Rollout em quatro estágios e o limite do shadow mode ("não dá pra shadow uma ação")
- **O que é**: promoção gradual com critério de saída por estágio: **shadow** (agente gera, humano envia; sem efeito no cliente) → **draft/co-pilot** (humano edita e envia) → **autônomo restrito** por intenção → **expansão** intenção a intenção, parando se qualquer gate falhar. Critérios típicos: shadow sai com resolução correta no volume set + zero ações incorretas no risk set; autônomo exige CSAT ≥ humano e recontato ≤ baseline humano. O insight não óbvio: shadow mode testa **resposta**, não **ação** — "either the money moves or it doesn't, so a refund tool is untestable in shadow by definition"; ações só se validam em sandbox/mocks (item 8) ou em canary com alçada baixa. Canary percentual (0,1–1% → 5 → 20 → 50 → 100, ≥24h por degrau) é a etapa seguinte ao shadow, não substituto.
- **Quem está shipping**: padrão descrito por Richpanel, FutureAGI, MLflow (2026) — prática, não produto. Vendors embutem "modo draft/copilot" (Zendesk Agent Copilot GA, Intercom, Decagon Duet).
- **Maturidade**: mainstream como prática de deploy; a distinção shadow-resposta vs. shadow-ação é o ponto novo.
- **Aplicação em motor de resolução**: feature flag por intenção × estágio; métricas do item 4 como gates; ferramentas de ação só liberadas no estágio 3 com alçada.
- **Gap vs blog**: não existe para suporte. Adjacente: `4-niveis-autonomia-agentic-code` (níveis de autonomia em coding) e `hands-on-pr-100-gerado-por-agente-laravel`. Ângulo novo: **estágios por intenção com critérios de saída numéricos** e a impossibilidade de shadow em ações com efeito.
- **Fontes**: https://www.richpanel.com/learn/evaluating-ai-support-agents-before-launch (2026) · https://futureagi.com/blog/agent-rollout-strategies-2026/ [secundário] · https://mlflow.org/articles/what-is-canary-deployment-ai (2026) · https://tianpan.co/blog/2026-04-09-llm-gradual-rollout-shadow-canary-ab-testing (09/04/2026) [secundário]

### 10. Ações transacionais seguras: idempotency key por efeito, ledger de estados, compensação e alçada
- **O que é**: o tool call que move dinheiro precisa dos mesmos cuidados de um sistema distribuído: (a) **operation ID gerado antes da primeira escrita externa e persistido com o estado** do workflow, composto de tenant + instância + passo + objeto de negócio + efeito pedido; contrato "same key + same intent → original result; same key + different intent → rejected"; (b) **ledger** PLANNED → VALIDATED → APPROVED → DISPATCHED → COMMITTED, com ramos OUTCOME_UNKNOWN e RECONCILING (timeout não prova que nada aconteceu); (c) **compensação** como ação nova de domínio (não rollback); (d) classificação de retry (não re-tentar negação de autorização nem escrita não-idempotente após outcome desconhecido); (e) alçada por ação: teto em dinheiro, frequência, exclusões de política, escopo mínimo de credencial (read em pedidos, write no Stripe até um cap); (f) **trilha de auditoria** com o motivo da decisão — Managed Agents grava `evaluated_permission` + `reason_code` por chamada; Sierra/Decagon expõem traces; o Commerce Agents blueprint da Anthropic (02/09/2026) deixa checkout com o varejista e exige aprovação humana para mudanças do merchant agent entrarem em vigor.
- **Quem está shipping**: Anthropic Managed Agents (audit via eventos), Anthropic Commerce Agents blueprint (02/09/2026, GitHub anthropics/commerce-agents, verticais retail/travel/telecom/ticketing), Fini (caps + audit log exportável) [secundário], StackOne; padrão descrito por vdf.ai (2026) e arXiv 2602.20214 ("Right to History", execução verificável).
- **Maturidade**: early adopters — o conhecimento existe em sistemas de pagamento, mas a adaptação ao tool calling (chave antes do LLM decidir, ledger no harness) ainda é artesanal.
- **Aplicação em motor de resolução**: camada de execução do harness entre o LLM e o sistema de registro: gera chave, grava PLANNED, checa alçada/política (item 3), pede aprovação se preciso (itens 5–6), despacha, reconcilia. No Laravel: job + tabela de ledger + `Idempotency-Key` no Stripe.
- **Gap vs blog**: não existe. Adjacente: `tool-use-na-pratica-desenhando-ferramentas-llm`, `tool-calling-nao-funciona` (design de schema/erros), `observabilidade-agentes-ia-…` (tracing). Ângulo novo: **tool de ação como transação distribuída** — chave de idempotência, ledger, compensação, alçada e audit com reason_code.

### 11. Voz speech-to-speech em produção: o que mudou em 2026 (gpt-realtime-2, SIP, MCP, Voice Sims)
- **O que é**: o pipeline STT→LLM→TTS foi substituído por modelo S2S único com raciocínio de fronteira. OpenAI gpt-realtime-2 (07/05/2026): Realtime API sai de beta; modelo de classe GPT-5, contexto 128K (antes 32K), tool calling melhorado, suporte a Agents SDK, **MCP remoto**, entrada de imagem e **telefonia via SIP**; separado em três primitivas (realtime-2, realtime-translate, realtime-whisper); snapshots de dez/2025 já traziam +12,9 pp em acerto de tool calling e ~90% menos alucinação na transcrição vs Whisper v2; preço −20% [secundário]. Do lado de teste, Sierra Voice Sims (set/2025, detalhado em 2026): dois loops trocando chunks de áudio — *simulated call loop* (persona com objetivo/humor/idioma/paciência, voz sintética "muddied" com ruído, DTMF, interrupções, fala sobreposta) e *voice loop* (o agente) — reexecutável de forma idêntica e julgado por LLM. Vendors: Intercom Fin Voice (resoluções *assumed* = desligou após resposta / *confirmed* = disse que estava resolvido / *routed*), Decagon Voice 2.0 + **outbound voice** (03/2026: detecta caixa postal, filtros anti-spam, compliance), Zendesk Voice AI Agents + contact center nativo GA (05/2026), Sierra voz em Agent OS 2.0.
- **Quem está shipping**: OpenAI (07/05/2026), Sierra, Intercom, Decagon, Zendesk, Salesforce Agentforce Voice.
- **Maturidade**: mainstream para inbound; early para outbound e para simulação de voz rigorosa.
- **Aplicação em motor de resolução**: mesmo procedimento (item 1) servindo chat e voz; em voz, o verificador (item 3) e a confirmação (item 5) precisam caber em latência sub-segundo — daí a separação em primitivas e a importância de MCP direto do modelo de voz. Voice Sims = item 7 aplicado a áudio.
- **Gap vs blog**: não existe nada de voz no acervo. Ângulo: **arquitetura S2S + SIP + MCP** e **como testar voz antes de atender** (dois loops, ruído, DTMF).

### 12. Memória de cliente cross-canal com governança (expiração, redação, API)
- **O que é**: memória no nível do **cliente**, não da sessão: histórico conversacional persistente entre sessões e canais (chat, voz, e-mail, SMS), sinais estruturados (preferência, sentimento, tentativas de contato) consolidados num perfil único — e, o que é novo em 2026, **controles de governança como feature**: "full API access, expiration controls, and built-in redaction policies" (Decagon). Sierra ADP (Agent Data Platform, 05/11/2025) é "the memory and intelligence layer of Agent OS", unindo não-estruturado (chamadas, chats) com estruturado (CRM, billing, políticas) para "next best actions" e resolução proativa. Salesforce ancora em Data 360. Anthropic Managed Agents expõe *memory store endpoints* (beta header `agent-memory-2026-07-22`) — indício de memória gerenciada no runtime, detalhes não verificados nesta pesquisa.
- **Quem está shipping**: Decagon User Memory (Proactive Agents, 03/2026); Sierra ADP (11/2025); Salesforce Agentforce 360 / Data 360 (GA, Dreamforce 2025); Anthropic Managed Agents memory store (beta 07/2026, **[parcialmente verificado]**).
- **Maturidade**: early adopters/mainstream nos vendors; governança (TTL, redação) ainda rara in-house.
- **Aplicação em motor de resolução**: o procedimento consulta o perfil antes do primeiro turno (evita "repita seu CPF"), o verificador usa histórico para detectar recontato (item 4) e abuso (ex.: 3º reembolso em 30 dias → alçada), e a retenção segue política (LGPD).
- **Gap vs blog**: **adjacente** a `memoria-de-agente-de-ia`, `memoria-agente-assistente-compras`, `pgvector-postgres-memoria-do-seu-agente`, `agente-ia-estado-entre-execucoes` (memória de agente/sessão). Ângulo novo: **perfil de cliente cross-canal como insumo de resolução** + expiração/redação como requisito de produto, não detalhe de infra.
