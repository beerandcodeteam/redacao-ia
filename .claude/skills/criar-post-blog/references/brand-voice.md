# Voz e tom — Beer & Code

> "O Beer & Code fala como um dev sênior experiente explicando o futuro da tecnologia para outros devs, com clareza, provocação, profundidade técnica e zero paciência para hype vazio."

Esse arquivo é a régua. Antes de publicar, releia. Se um trecho do post não bate com o que está aqui, reescreve.

## O que o Beer & Code é (e o que não é)

**É:**

- Autoridade técnica que fala a língua do dev real.
- Mistura de clareza técnica + provocação + didática + proximidade + visão de mercado.
- Quem está no campo de batalha construindo software de verdade.

**Não é:**

- Escola tradicional.
- Consultoria corporativa engessada.
- Comunidade motivacional genérica.
- Marketing de infoproduto.

## Tese central

> "Desenvolvedor bom não é quem sabe copiar código. É quem entende o problema, modela a solução e entrega software que funciona no mundo real."

Atualizada para o posicionamento atual:

> "O próximo salto do desenvolvedor não é usar IA. É saber construir produtos reais com IA."

Todo post deve, direta ou indiretamente, reforçar essa tese.

## Personalidade da marca

Quatro lados que coexistem:

1. **Professor técnico de verdade.** Profundidade sem enrolação. Não fala difícil para parecer inteligente. Fala simples porque domina.
2. **Dev raiz, sem paciência para firula.** Cutuca o mercado, escola tradicional, dev acomodado. Sem arrogância gratuita.
3. **Líder de comunidade.** Fala como quem está dentro do grupo. Gera sensação de "aqui tem gente séria, aqui tem direção".
4. **Antihype, mas atento ao futuro.** Não nega tendências. Mas não compra hype barato.

## Ritmo

Frases curtas.

Com pausas.

Como se fosse uma fala.

Exemplo:

> O problema não é a IA.
>
> O problema é o dev achar que usar IA é pedir código para o Cursor.
>
> Isso não é engenharia.
>
> Isso é terceirizar raciocínio.
>
> Engenharia de IA começa quando você entende contexto, dado, intenção, recuperação, avaliação e limite do modelo.

Esse ritmo serve para post, story, reel, e-mail e WhatsApp. Em post longo, intercale frases curtas com explicações um pouco mais densas — não fica tudo staccato.

## Como falar de tecnologia

Não basta dizer "vamos aprender embeddings".

Sempre estrutura: **conceito técnico + aplicação prática + impacto no produto.**

Exemplo bom:

> Embeddings são uma forma de transformar texto, imagem ou comportamento em representação matemática. É isso que permite construir busca semântica, recomendação de conteúdo, memória de usuário, classificação inteligente e sistemas que entendem similaridade em vez de só comparar palavras.

## Tom comercial (CTA)

CTA é convite, não pitch. O destino (evento, Clã, repositório, newsletter) vem como input do post e é integrado ao texto — **nunca** vira seção separada com heading.

Quando o destino for o **Clã Beer and Code ou um evento da marca**, o conteúdo do CTA (ângulo do argumento, nível de intensidade, dados que podem ou não entrar) vem da skill `montar-cta-pitch` — as regras de forma abaixo continuam valendo por cima.

### Regras (obrigatórias)

1. **Sem heading dedicado.** Nada de `## CTA`, `## Entra no Clã`, `## Inscreva-se`, `## Próximos passos`, `## Quer ir além?`, etc. O destino entra na prosa.
2. **Sem caixa, sem blockquote isolado, sem `---` ao redor.** Não destaque visualmente. O leitor que volta ao texto não deve sentir uma pausa comercial.
3. **1–2 frases curtas, dentro de um parágrafo de prosa normal.** Posição default: **primeiro terço do post (~30% da leitura)**, num trecho onde o tema conversa diretamente com o destino — o leitor de news-jacking raramente chega à conclusão. Conclusão só como fallback quando não houver encaixe natural antes.
4. **Link inline em Markdown puro:** `[nome do destino](url)`. Sem botão, sem badge, sem "→ clique aqui".
5. **Tom.** Convite curto, sem hard sell. Sem "imperdível", "última chamada", "vagas limitadas", "garanta sua vaga", "não fique de fora".
6. **Teste mental.** Se o leitor pular o link e continuar lendo, a frase ainda fecha o raciocínio. Se a frase só funciona como vendedora, voltou pra prancheta.

### Exemplos do formato (o conteúdo varia com o post)

> ...esse é exatamente o tipo de pipeline que vamos destrinchar ao vivo no [Beer & Code Summit](url): código rodando, decisões de arquitetura na mesa, sem slide motivacional.

> ...se você quer ver isso aplicado em PHP de verdade, com benchmarks e dor de produção, é o que rola toda semana no [Clã](url).

> ...próximo passo é olhar o repositório de referência: [exemplo-rag-laravel](url). Tem o código completo desse post, com testes e dataset de 50 casos.

A diferença entre CTA chato e CTA bom é uma só: o leitor termina a frase sentindo que ganhou um próximo passo concreto, não que entrou num funil.

### Quando o post não tem destino de CTA

Sai sem CTA. A conclusão fecha no técnico mesmo (resumo + provocação + link interno para post relacionado). Não invente CTA genérico ("siga o blog", "compartilhe").

## Tom emocional

Maduro, não apelativo. Liga em:

- medo de ficar para trás
- frustração por estar estagnado
- desejo de ser respeitado tecnicamente
- cansaço de conteúdo superficial
- comparação com devs que estão evoluindo mais rápido

Não usa fórmula motivacional barata.

## "Inimigos narrativos" (use com parcimônia, sem virar reclamação)

1. Escola tradicional de programação que vende conteúdo superficial sem prática real.
2. Hype vazio em IA — prompt mágico, automação frágil, "agente" que não aguenta produção.
3. Complexidade desnecessária — overengineering, DDD de pasta, microsserviço sem necessidade, clean architecture aplicada sem contexto.
4. Dev copia-e-cola — crítica ao comportamento, não pessoal.
5. Generalismo sem direção — querer aprender tudo ao mesmo tempo e não ter profundidade em nada.

Cutucar é OK. Sermão chato não.
